# 生圖這條路：把當下的角色變成一張照片

[English／程式對照](IMAGES.md) · [模型與下載方式](MODELS.md) · [回首頁](../README.zh-TW.md)

**不用每次重寫一大段Prompt：先讀取角色的現況，再把你這次想拍的樣子組成照片。**
圖片模型負責畫圖；我們這套負責整理「是誰、穿什麼、在哪裡、現在幾點、這次怎麼拍」。

## 完整流程，建議用 `/photo`

![完整的角色照片流程](diagrams/image-pipeline.svg)

```text
/photo 保持現在穿著，閉上眼睛，從側面拍一張，拿著茶杯。
```

1. **抓當前快照**：固定外觀、目前穿著、妝髮、飾品、配件、地點、背景與時間光線。
2. **挑近期場景線索**：從最近12則紀錄中，挑同一角色所在地、20分鐘內的資料，最多6則。
3. **本地模型做視覺規劃**：決定表情、有限的姿勢選項、角度，以及有來源的道具／單張換裝提案。
4. **Python組最終Prompt**：把程式負責的外觀、背景、光線放回，驗證提案後各區塊只組一次。
5. **保存成圖片工作**：確切Prompt進SQLite佇列，再由獨立工作程序執行。
6. **MFLUX呼叫圖片模型**：產生圖片並傳到Telegram；成功後可以查最終Prompt，暫存圖會清理。

**不是整條路都沒用9B。** 視覺規劃仍會呼叫目前的本地聊天模型；
但最終Prompt是Python組裝，並不是讓9B自由重寫外觀、衣著、背景與光線。
規劃失敗時會退回已知現況和有限的明確要求處理，不能保證所有拍攝要求都留下。

若用普通聊天要求照片，還會先經過一般Observer／Writer回覆流程，再接生圖。
`/photo`本身是指令路徑，不需要為了拍照先走一輪普通對話。
快照在準備工作時固定，排隊途中角色換地方，不會把這張照片偷偷換成新場景。

## Prompt每一段由誰負責？

![生圖Prompt的欄位分工](diagrams/image-layers.svg)

| 區塊 | 怎麼來 |
|---|---|
| 固定外觀 | 角色設定的辨識特徵；不每張重新猜一個人。明確暫時變身另需本次要求證據。 |
| 目前衣著 | 讀現況衣著槽，而不是「平常喜歡穿什麼」的偏好清單。已脫下與未知不同。 |
| 妝髮 | 讀目前髮型、妝容；長髮可以盤起，不代表必須披髮。 |
| 飾品／配件 | 耳環等飾品與包包等裝備分開。 |
| 表情／姿勢 | 這次要求配合受限規劃；「閉眼」等常見明確要求有程式處理。 |
| 道具 | 依本次要求與近期來源選取，目前支援茶杯、書本、花朵，最多兩種。擺茶杯不代表已泡好或喝過。 |
| 背景 | 依目前地點查已登錄背景，不讓每次模型自由補一間臥室。未匹配地點也不硬貼室內模板。 |
| 時間／光線 | 固定這張照片的時間，再依室內／戶外設定光線；目前helper明確使用台北時區。 |
| 鏡頭 | `/photo`是使用者看角色的虛擬視角；方向、俯仰與景別分開。沒指定時不固定加半身構圖。 |

最終順序大致是：

```text
固定外觀 → 暫時變化（若有） → 衣著 → 飾品／配件 → 妝髮
→ 表情 → 姿勢 → 道具（若有） → 背景 → 時間光線 → 鏡頭
```

要求會整理到相應欄位，不會再把「使用者要求：……」整段當故事塞進去。
圖片模型使用自己的文字編碼器與VAE，並沒有把我們聊天的9B拿去當圖片編碼器。

## 換這張照片的衣服，不等於修改角色現況

```text
/photo 這張穿紅色外套。
```

通過來源驗證的換裝只套用這張照片。要真的改目前穿著，請用 `/settings` 或 `/outfit`。
道具與鏡頭也屬於拍攝安排，不是故事動作完成的證據，更不會因此移動使用者。
角色正式換場和預設換裝，由前面的狀態／旅程系統負責。

## 四種入口不能混為一談

| 入口 | 現在的行為 |
|---|---|
| **`/photo 描述`** | 最完整的現況照片路徑：快照、視覺規劃、受控組裝、排隊生圖。 |
| **聊天中要求拍照** | 一般對話後，判定需要照片才接視覺流程；視角依判定種類。 |
| **`/selfie 描述`** | 較簡單的固定外觀、當前衣著／配件前綴加描述；沒有完整`/photo`背景與時間組裝。 |
| **`/image 描述`** | 直接把描述用來生圖，不自動套用角色與穿著。 |
| **角色第一人稱所見** | 畫環境，不是使用者看著角色；通常不帶角色肖像區塊。 |

因此展示「跟著角色場景拍照」時，建議用`/photo`，不要把所有指令都宣傳成同一個功能。

## 一份可檢查的組裝例子

合成角色林青28歲，在21:15的花園，穿灰色針織外套、白色上衣與深色長褲。
輸入「保持穿著、閉眼、側面、拿茶杯」後，實際Python組裝結果保留當前衣著，
加入閉眼、坐姿、茶杯、戶外夜景與側面鏡頭，沒有預設半身。

[看快照、手動規劃值與完整Prompt](examples/photo-context.json) · [直接看最終Prompt](examples/photo-prompt.txt)

這個例子只驗證組裝；規劃值是手動提供的合成資料，沒有重播真人對話，也沒有新呼叫模型或生成圖片。
首頁的Bot大頭照是專案形象圖，不拿它冒充這個例子的實測成果。

## 完成後可以追查，也不必留一堆圖片

圖片佇列最多5個未完成工作，一次處理一張。MFLUX是獨立短生命週期程序，
完成Telegram上傳後可以用`/prompt`或檢視頁「最近生成」看最終Prompt。
成功或失敗後會清理暫存圖片，但Prompt／工作診斷紀錄仍可能保留；這不等於刪除Telegram上的照片。
圖片生成時聊天仍可能因記憶體／GPU競爭變慢，不能保證送達恰好一次。
拍照工具回合與一般聊天記憶分工，正式狀態變化和診斷紀錄另算。

我們最值得展示的是**把現況、要求、背景與鏡頭整理成可重用、可追查的生圖流程**。
目前是Prompt層的一致性，沒有參考照片鎖臉、ControlNet或固定臉模型；
畫圖品質、人體結構、臉部一致性仍受權重影響。狀態記錯也會讓照片跟著錯。
目前光線helper固定台北時區，單改聊天的`TIMEZONE`不會一併泛化它。

實際開發配置為Z-Image Turbo／MFLUX 4-bit、512×512、9步，詳見[模型清單](MODELS.md)。
