# 六個核心：誰判斷、誰記憶、誰開口？

[English](ARCHITECTURE.md) · [回專案首頁](../README.zh-TW.md)

以下依目前已公開的程式整理。「核心」是職責名稱，不代表六個模型或六個服務。
**藍色為本地模型呼叫，綠色為 Python 規則／組裝，黃色為資料。**

## 一、六個核心怎麼分工？

![六個核心與資料交接](diagrams/cores.svg)

| 核心 | 收到什麼 | 交出什麼 | 是否生成式模型 |
|---|---|---|---|
| **理解核 Observer** | 本輪原文、現況、選取的近期對話與記憶 | 事件提案、話語意圖、取材範圍與有證據的評估 | 是；實驗台可明確沿用同一起點的判讀快取 |
| **決策核 Decision** | 通過驗證的事件、性格、情緒、關係與需求 | 選定的行為、目標、條件與骨幹相關欄位 | 否，Python計分／規則 |
| **口吻核 Delivery** | 計算後的口吻值、定案行為與交談投入 | 給Writer看的自然語言口吻指示 | 否，查表與護欄 |
| **故事核 StoryCore** | 有來源的舊對話、筆記、話題、到訪與生活紀錄 | 本輪相關的單一 `story_context` 與後端來源稽核 | 整理閱讀包不呼叫生成模型；檢索可選用嵌入模型 |
| **編輯核 Editor** | 身份、正式事實、定案、口吻、記憶與近期原文 | 控制容量後的最終 `messages` | 否；計token可能聯絡本地伺服器 |
| **Writer** | 最終 `messages` | 角色實際回覆 | 是 |

另外有一個共用的**狀態機／Reducer**：它確認事件證據、人物、地點、穿著與完成階段。
Observer 說「抵達」只是提案；通過驗證才更新正式狀態。決策、口吻、故事核並不是各自一套任意改事實的模型。

編輯核也不是新增的第七次判斷；它是現有 `prepare_writer`、`ContextPlanner`、
`finish_contract`、`writer_projection` 與回答骨幹函式的職責分組。
[實際程式對照表與可編輯Mermaid來源](ARCHITECTURE.md#1-six-cores-what-each-one-produces)

## 二、一句話實際走的順序

![前景對話與回覆後分析](diagrams/turn.svg)

1. Telegram收進文字，最後一則普通文字後等10秒，把相鄰訊息合併。
2. 推進時間、載入現況、凍結本輪起點，再選取相關記憶。
3. **第一次模型呼叫：Observer**，理解原文中的意圖與事件。
4. Python驗證並更新接受的狀態，再評估需求、比較候選行為。
5. 產生回答骨幹、查口吻表，由編輯核組成Writer Prompt。
6. **第二次模型呼叫：Writer**，將定案寫成對話，送達Telegram。
7. 普通Telegram路徑在送達後，才安排背景分析實際回文，將通過驗證的變化寫回。

所以前景一般是**兩次主要生成呼叫，不是每個core各呼叫一次**。
回覆後分析、舊對話整理、生活事件續寫、媒體／外部工具或故障恢復可能增加呼叫；
不能把兩次當成所有情況的固定總數。照片與Web測試路徑的保留／分析方式亦可不同。

回覆後分析是理解「角色真的說了什麼」，不是一個送出前保證品質的Judge。
目前小模型即使拿到正確Prompt，仍可能混淆或補寫細節。

## 三、故事核和生活系統，不是同一件事

![歷史取材與虛構生活的分工](diagrams/story-life.svg)

**故事核負責過去：**「我們聊過什麼？哪段和現在有關？」
它依來源、人物、時間、場景與話題選取資料，避免相同來源重複塞入Prompt。
使用者自己的生活話題可以跨場景延續，不會因角色換房間就失去連結。
本輪的 `query/packet/render` 並不是再叫9B自由編一段故事。

**生活系統負責角色日常：**「角色今天安排什麼？現在的虛構事件進展到哪？」
公開示範世界的行程查年度表；事件草稿、進展、是否已告知使用者另有紀錄。
符合條件時可由本地模型產生受限制的下一步事件；其他設定的世界仍可走模型規劃。
它模擬的是角色的虛構生活，不代表現實行動。

**主動訊息是第三個環節：** 有生活進展不代表直接傳訊息。
候選還要通過安靜時段、冷卻、移動中與否等條件，交給同一決策核選擇，再由Writer表達。
這條路沒有新的使用者原文，不需先跑一次User Observer。換場通知另有路徑，不能和一般主動話題混為一談。

## 四、編輯核到底交什麼給Writer？

![編輯核組成最終輸入](diagrams/editor.svg)

主要交接的是：

- **身份與必要現況**：誰在說話、對誰說，現在時間與本輪相關的正式狀態。
- **定案骨幹**：要回答、答應、婉拒或其他行為；不把整張候選分數表交給Writer重選。
- **口吻**：如何表達，而不是重新決定立場。
- **選取後的故事／近期對話**：有來源、去重、符合本輪問題範圍。

編輯核控制取材與token容量，不是語義正確性的保證器。
必要內容仍放不下時會停止；也不能保證Writer完全照做。

診斷資料庫只讓人追查；檢視頁的三份資料是**同一輪Observer輸入、原始輸出、Writer Prompt**，
不會把診斷庫讀回角色記憶。圖中省略語音、圖片、設定面板等周邊接線；
L0–L3試作、舊Harness與uzu不在目前公開版正式流程內。

生圖另有獨立的快照、視覺規劃與Python組裝，詳見[完整生圖流程](IMAGES.zh-TW.md)。
